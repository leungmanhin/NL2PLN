
# PeTTaChainer PLN surface language for `add_atom()` and `query()`

This reference describes the expression strings to pass to the Python API. Do not include MeTTa command wrappers such as `!(compileadd ...)` or `!(query ...)` in Python API strings; the Python methods add those wrappers internally.

---

## 1. Expression format

### Statement / assertion passed to `add_atom(...)`

All facts and rules passed to `add_atom()` use this envelope:

    (: proof-id proposition truth-value)

Examples:

    (: f1 (Dog fido) (STV 1.0 1.0))

    (: r1
       (Implication
          (Premises (Dog $x))
          (Conclusions (Animal $x)))
       (STV 1.0 1.0))

Constraints for statements:

- `proof-id` must not be a variable. Use an atom such as `f1`, `rule1`, or an expression such as `(no_inverse rule1)`.
- `proposition` is the fact/rule content. It is usually a predicate-like S-expression such as `(Dog fido)` or an `Implication`.
- `truth-value` must be one of the supported truth/value forms listed in §3.
- Variables are written with a leading `$`, e.g. `$x`, `$person`, `$dist`.
- Constants and predicate symbols are ordinary MeTTa atoms or nested expressions. They match syntactically.

### Query passed to `query(...)`

All queries passed to `query()` use this envelope:

    (: $proofVar proposition-pattern $tvVar)

Example:

    (: $prf (Dog fido) $tv)

The proof slot must be a variable. The usual TV slot is also a variable, but the validator’s hard requirement is the variable proof slot. The Python method supplies the search budget via its `steps` argument, so do not write `!(query steps kb ...)` in the query string.

## 2. Built-in operators and writable surface forms

### 2.1 Plain predicate / proposition form

Surface syntax:

    (Predicate arg1 arg2 ...)
    (Predicate nested-term ...)
    Symbol

A plain predicate has no built-in meaning beyond syntactic matching and rule chaining. For example, `(Dog fido)`, `(Own alice dog1)`, and `(AtTime (FeatureX 0) 1)` are all user-level propositions.

A unary predicate is the normal idiom for class membership:

    (Dog fido)
    (Person alice)
    (City paris_fr)

### 2.2 Statement envelope `:`

Surface syntax:

    (: proof-id proposition truth-value)

This is the required assertion/query envelope. In statements, it asserts that `proposition` has `truth-value` with provenance `proof-id`. In queries, it asks for matching proof/proposition/TV triples.

### 2.3 Rules: `Implication`, `Premises`, `Conclusions`

Surface syntax:

    (: rule-id
       (Implication
          (Premises premise1 premise2 ...)
          (Conclusions conclusion1 conclusion2 ...))
       (STV s c))

Semantic effect:

- If the premises can be proven, the conclusions can be derived.
- Premises are combined conjunctively.
- The rule’s `STV` is used as the implication strength/confidence.
- A single conclusion is the common case.
- Multiple conclusions are allowed and are treated as a compound conjunction-like conclusion; the system can also project components of compound conclusions.

Canonical example:

    (: dog_to_animal
       (Implication
          (Premises (Dog $x))
          (Conclusions (Animal $x)))
       (STV 1.0 1.0))

### 2.4 Compound connectors: `And`, `Or`, `LikelierThan`

These heads are recognized as compound proposition forms.

#### `And`

Surface syntax:

    (And expr1 expr2 ...)

Semantic effect:

- Combines multiple propositions conjunctively.
- The resulting `STV` uses the minimum strength and minimum confidence of the component TVs.
- In queries, it can retrieve bindings satisfying all conjuncts.
- In rules, it can be used explicitly as a premise or conclusion term, although multiple entries in `Premises` are usually clearer.

Example query:

    (: $prf (And (Own alice $x) (Pet $x)) $tv)

#### `Or`

Surface syntax:

    (Or expr1 expr2 ...)

Semantic effect:

- Recognized as a compound proposition connector.
- The built-in TV formula combines two TVs using minimum strength and maximum confidence.
- It is less commonly used in the tests/specs than `And`; prefer explicit rules unless disjunction is really intended.

#### `LikelierThan`

Surface syntax:

    (LikelierThan expr1 expr2)

Semantic effect:

- Recognized as a compound proposition connector.
- The built-in TV formula compares component strengths and returns the TV with the larger strength, with confidence equal to the minimum of the two confidences.
- This is specialized and should only be generated when the intended proposition is a likelihood comparison between two already-TV-bearing propositions.

### 2.5 `Compute`

Surface syntax in rule premises, preferred:

    (Compute function (arg1 arg2 ...) -> output)

Also accepted in some contexts:

    (Compute function (arg1 arg2 ...) output)

Semantic effect:

- Runs a MeTTa function/operator on the arguments and binds or checks the output.
- Arithmetic functions such as `+`, `-`, `*`, and `/` are used in tests.
- A successful compute premise contributes a unit truth value unless it is one of the special formula computations handled by the runtime.
- In ordinary rule premises, prefer the arrow form.
- In direct compound queries containing `And`, the non-arrow form is used in tests and is the safest form for compute-inside-query patterns.

Examples:

    (Compute + ($n 1) -> $n1)

    (: $prf
       (And (P $x) (Compute + ($x 1) $y) (P $y))
       $tv)

### 2.6 `Not`

Surface syntax:

    (Not expr)

Semantic effect:

- Negates the truth value of a proven `expr`.
- If `expr` has `(STV s c)`, then `(Not expr)` has `(STV (- 1 s) c)`.
- This is truth-value negation over a matched/proven expression, not classical negation-as-failure. Do not use it to mean “there is no known proof of expr” unless that modeling choice is intentional.

### 2.7 Distribution comparison: `GreaterThan` and `>`

Surface syntax:

    (GreaterThan dist threshold)
    (> dist threshold)
    (GreaterThan distA distB)
    (> distA distB)

Semantic effect:

- Used as a premise/query helper over distribution-valued terms.
- Distribution vs numeric threshold returns an `STV` whose strength is the probability that the distribution’s value is greater than the threshold.
- Distribution vs distribution returns an `STV` whose strength is the probability that a sample from `distA` is greater than a sample from `distB`.
- Confidence for particle distributions is derived from effective sample size; distribution-vs-distribution confidence is the minimum confidence of the two distributions.

Recommended patterns:

    (HeightDist countryA $distA)
    (HeightDist countryB $distB)
    (GreaterThan $distA $distB)

    (CountDist room1 $countDist)
    (GreaterThan $countDist 1)

### 2.8 Aggregation: `FoldAll`

Surface syntax:

    (FoldAll pattern value init fold-fn -> out)

Semantic effect:

- Finds all matches of `pattern`.
- For each match, extracts `value`.
- Folds the extracted values starting from `init` using `fold-fn`.
- Binds the aggregate result to `out`.
- The aggregate premise itself has unit truth when successfully computed.

Example:

    (FoldAll (Score $name $n)
             $n
             0
             (|-> ($acc $elem) (+ $acc $elem))
             ->
             $total)

This can derive a total score/count-like value.

### 2.9 Aggregation over truth values: `FoldAllValue`

Surface syntax:

    (FoldAllValue pattern init fold-fn -> out)

Semantic effect:

- Finds all matches of `pattern`.
- Folds over the truth values of the matching facts, rather than over a separate extracted value expression.
- Useful for turning uncertain memberships into a distribution.

Typical pattern:

    (FoldAllValue (In $room $kid)
                  (ParticleFromPairs ((0 1.0)))
                  ParticleAddBernoulliFromSTV
                  ->
                  $countDist)

Here each matching `(In $room $kid)` contributes according to its `STV`, producing a particle distribution over counts.

### 2.10 Distribution mapping: `MapDist`

Surface syntax:

    (MapDist function
             (DistFact ... inputDist)
             inputDist
             ->
             outputDist)

Semantic effect:

- Matches a fact containing a distribution.
- Applies a unary function to the distribution’s samples.
- Binds the resulting distribution.

Example pattern:

    (MapDist f (InputDist $x $inDist) $inDist -> $outDist)

### 2.11 Binary distribution mapping: `Map2Dist`

Surface syntax:

    (Map2Dist function
              (DistFactA ... distA)
              distA
              (DistFactB ... distB)
              distB
              ->
              outputDist)

Semantic effect:

- Matches two distribution-bearing facts.
- Applies a binary function to samples from the two distributions.
- Binds the resulting distribution.

Example:

    (Map2Dist *
       (LengthDist $rect $lengthDist)
       $lengthDist
       (WidthDist $rect $widthDist)
       $widthDist
       ->
       $areaDist)

### 2.12 Average distribution: `AverageDist`

Surface syntax:

    (AverageDist pattern valueDist -> avgDist)

Semantic effect:

- Matches all facts satisfying `pattern`.
- Extracts a distribution-valued field `valueDist` from each match.
- Produces a distribution for their average.

Example:

    (AverageDist (HeightDist $group $person $heightDist)
                 $heightDist
                 ->
                 $avgDist)

### 2.13 Distribution constructors and functions

These are writable in facts/rules/queries wherever a value term is needed, especially as a distribution-valued argument or TV.

#### `PointMass`

    (PointMass x)

A degenerate particle distribution concentrated at exactly `x`.

#### `ParticleFromNormal`

    (ParticleFromNormal mu sigma)

Creates a deterministic normal-like particle approximation centered at `mu` with spread `sigma`.

#### `ParticleFromPairs`

    (ParticleFromPairs ((x1 w1) (x2 w2) ...))

Creates a particle distribution from explicit weighted samples.

#### `NatDist` and `FloatDist`

    (NatDist ((value probability) ...))
    (FloatDist ((value probability) ...))

Exact small discrete distributions. `NatDist` is for natural-number-like values and `FloatDist` for floating values.

#### `ParticleDist`

    (ParticleDist ref)
    (ParticleDist ref scale)

Opaque particle distribution reference. In normal generated expressions, prefer constructors such as `PointMass`, `ParticleFromNormal`, or `ParticleFromPairs`; `ParticleDist` references are usually produced by evaluation.

#### `DistGreaterThanFormula`

    (DistGreaterThanFormula dist threshold)

Returns an `STV` for the probability that `dist > threshold`.

#### `DistGreaterThanDistFormula`

    (DistGreaterThanDistFormula distA distB)

Returns an `STV` for the probability that `distA > distB`.

#### `ParticleMap`

    (ParticleMap function particleDist)

Unary sample-wise map over a particle distribution.

#### `ParticleMap2`

    (ParticleMap2 function particleDistA particleDistB)

Binary sample-wise composition of two particle distributions.

#### `ParticleAddBernoulliFromSTV`

    (ParticleAddBernoulliFromSTV particleDist stv)

Updates a count-like particle distribution by adding a Bernoulli contribution whose probability is taken from the `STV` strength.

#### `CondDistFromJoint`

    (CondDistFromJoint jointDist inputDist bandwidth)

Constructs a conditional distribution from a joint distribution and an input distribution using a similarity bandwidth. This is specialized; generate it only for explicit conditional-distribution modeling.

### 2.14 Proof-id idiom: `no_inverse`

Surface syntax in proof-id position:

    (: (no_inverse rule-id)
       (Implication ...)
       (STV s c))

Semantic effect:

- This is not a proposition connector.
- It is a surface proof-id idiom used to prevent automatic inverse-rule behavior for that implication.
- Use ordinary proof ids by default. Use `(no_inverse rule-id)` only when the intended rule should be applied forward/backward in the direct implication direction without generating inverse estimates.

## 3. Truth values and uncertainty

Supported truth/value forms in the TV slot are:

    (STV strength confidence)
    (NatDist ((value probability) ...))
    (FloatDist ((value probability) ...))
    (ParticleDist ref)
    (ParticleDist ref scale)
    (PointMass x)
    (ParticleFromNormal mu sigma)
    (ParticleFromPairs ((x1 w1) (x2 w2) ...))

### `STV`

    (STV strength confidence)

- `strength` is belief/probability-like mass, normally in `[0, 1]`.
- `confidence` is evidence/reliability, normally in `[0, 1]`.
- Use `STV` for truth uncertainty: whether a proposition is true.
- Do not use `STV` strength to encode a numeric measurement such as height, price, or count.

Example:

    (: d1 (Dog fido) (STV 1.0 1.0))
    (: maybe_rain (Rainy tomorrow) (STV 0.6 0.8))

### Numeric/value uncertainty

Use distributions for uncertain numeric values.

Two modeling styles are accepted:

1. Distribution in the proposition term, with an `STV` for truth/existence:

       (: h1 (HeightDist group1 alice (PointMass 160.0)) (STV 1.0 1.0))
       (: h2 (HeightDist group1 bob (ParticleFromNormal 170.0 2.0)) (STV 1.0 1.0))

   This is the clearest recommended pattern for rules over numeric distributions.

2. Distribution in the TV slot:

       (: h1 (HeightDist group1 alice) (PointMass 160.0))

   This is accepted by the validator, but it mixes the assertion’s TV slot with value uncertainty. Prefer style 1 when generating new expressions.

## 4. Rule composition patterns

### 4.1 Canonical if-then rule

Natural language: “If X is a dog, then X is an animal.”

    (: dog_to_animal
       (Implication
          (Premises (Dog $x))
          (Conclusions (Animal $x)))
       (STV 1.0 1.0))

### 4.2 Multi-premise rule

Natural language: “If X is a dog and X lives in H, then X is a pet in H.”

    (: pet_in_home_rule
       (Implication
          (Premises
             (Dog $x)
             (LivesIn $x $h))
          (Conclusions
             (PetInHome $x $h)))
       (STV 1.0 1.0))

Premises are conjunctive. Their TVs are combined with `And` semantics: minimum strength and minimum confidence.

### 4.3 Explicit `And` premise

Equivalent pattern using `And` explicitly:

    (: expert_rule
       (Implication
          (Premises
             (And (IndustryVeteran $p) (ManagedTeam $p)))
          (Conclusions
             (Expert $p)))
       (STV 1.0 0.95))

Prefer separate premises for simple conjunctions unless the compound `And` itself is intended as a proposition.

### 4.4 Multi-conclusion rule

    (: multi_conclusion_rule
       (Implication
          (Premises
             (Parent $x $y))
          (Conclusions
             (Ancestor $x $y)
             (Related $x $y)))
       (STV 1.0 1.0))

Multiple conclusions are allowed. For clarity and predictable proof behavior, a translator may instead generate separate single-conclusion rules unless the conjunction of conclusions is specifically intended.

### 4.5 Rule with computation

    (: next_count_rule
       (Implication
          (Premises
             (CountAtTime $thing $t $n)
             (Compute + ($t 1) -> $t1)
             (Compute + ($n 1) -> $n1))
          (Conclusions
             (CountAtTime $thing $t1 $n1)))
       (STV 1.0 1.0))

Use `Compute` to derive numeric or functional intermediate values.

### 4.6 Rule with negation

    (: not_dog_rule
       (Implication
          (Premises
             (Not (Dog $x)))
          (Conclusions
             (NonDog $x)))
       (STV 1.0 1.0))

Remember that `Not` negates the TV of a matched/proven expression. It is not absence-of-proof.

### 4.7 Rule comparing distributions

    (: taller_rule
       (Implication
          (Premises
             (HeightDist countryA $distA)
             (HeightDist countryB $distB)
             (GreaterThan $distA $distB))
          (Conclusions
             (Taller countryA countryB)))
       (STV 1.0 1.0))

The comparison contributes an `STV` based on `P(distA > distB)`.

### 4.8 Rule mapping one distribution

    (: mapped_rule
       (Implication
          (Premises
             (InputDist $x $inDist)
             (MapDist f (InputDist $x $inDist) $inDist -> $outDist))
          (Conclusions
             (OutputDist $x $outDist)))
       (STV 1.0 1.0))

### 4.9 Rule combining two distributions

    (: area_rule
       (Implication
          (Premises
             (Rectangle $rect)
             (Map2Dist *
                (LengthDist $rect $lengthDist)
                $lengthDist
                (WidthDist $rect $widthDist)
                $widthDist
                ->
                $areaDist))
          (Conclusions
             (AreaDist $rect $areaDist)))
       (STV 1.0 1.0))

### 4.10 Rule averaging distributions

    (: avg_height_rule
       (Implication
          (Premises
             (Group $g)
             (AverageDist
                (HeightDist $g $person $heightDist)
                $heightDist
                ->
                $avgDist))
          (Conclusions
             (AvgHeightDist $g $avgDist)))
       (STV 1.0 1.0))

### 4.11 Rule counting uncertain memberships

    (: count_kids_rule
       (Implication
          (Premises
             (Room $room)
             (FoldAllValue
                (In $room $kid)
                (ParticleFromPairs ((0 1.0)))
                ParticleAddBernoulliFromSTV
                ->
                $cnt))
          (Conclusions
             (CntKidIn $room $cnt)))
       (STV 1.0 1.0))

Then a second rule can threshold the count distribution:

    (: crowded_rule
       (Implication
          (Premises
             (CntKidIn $room $cnt)
             (GreaterThan $cnt 1))
          (Conclusions
             (Crowded $room)))
       (STV 1.0 1.0))

### 4.12 Rule with aggregation over values

    (: total_score_rule
       (Implication
          (Premises
             (FoldAll
                (Score $name $n)
                $n
                0
                (|-> ($acc $elem) (+ $acc $elem))
                ->
                $total))
          (Conclusions
             (TotalScore $total)))
       (STV 1.0 1.0))

## 5. Query patterns and constraints

### 5.1 Ground-fact existence query

    (: $prf (Dog fido) $tv)

Returns proofs and TVs for known or derivable `(Dog fido)`.

### 5.2 Binding retrieval query

    (: $prf (Dog $x) $tv)

Retrieves bindings for `$x`.

### 5.3 Query derived facts

Given rules in the KB:

    (: $prf (Animal fido) $tv)
    (: $prf (Animal $x) $tv)

### 5.4 Query a distribution-valued result

    (: $prf (AvgHeightDist group1 $avgDist) $tv)

The distribution variable is inside the proposition. The `$tv` describes the truth/existence of the derived proposition.

### 5.5 Compound conjunction query

    (: $prf (And (Own alice $x) (Pet $x)) $tv)

This retrieves `$x` satisfying both conjuncts.

### 5.6 Compound query with computation

Use the non-arrow `Compute` form inside direct `And` queries:

    (: $prf
       (And (P $x) (Compute + ($x 1) $y) (P $y))
       $tv)

This finds pairs where `$y = $x + 1` and both `(P $x)` and `(P $y)` are provable.

### 5.7 Aggregate query

    (: $prf
       (FoldAll
          (Score $name $n)
          $n
          0
          (|-> ($acc $elem) (+ $acc $elem))
          ->
          $total)
       $tv)

This directly queries an aggregate result.

### 5.8 Query constraints

- The proof slot must be a variable:

      (: $prf (Dog fido) $tv)

  Do not write:

      (: proof1 (Dog fido) $tv)

- Do not pass command wrappers to the Python API:

      wrong for Python API: !(query 10 kb (: $prf (Dog fido) $tv))

- The proposition pattern may be ground, partially variable, compound, or even very broad. Very broad queries such as `(: $prf $type $tv)` are syntactically possible but expensive and usually discouraged for NL translation.
- Prefer a variable TV slot (`$tv`) unless intentionally filtering by a known TV pattern.
- Query variables are existential/retrieval variables. The query asks for bindings that make the pattern provable.

## 6. Quantification and scope

### 6.1 Universal quantification

There is no explicit universal quantifier operator such as `ForAll`.

Variables in rule premises/conclusions behave as rule variables: a rule applies for all bindings that satisfy the premises. For NL “all/every” statements, generate an implication rule.

Natural language: “Every dog is an animal.”

    (: every_dog_animal
       (Implication
          (Premises (Dog $x))
          (Conclusions (Animal $x)))
       (STV 1.0 1.0))

### 6.2 Existential quantification

There is no explicit existential quantifier operator for user expressions.

Common existential meanings are represented indirectly:

1. Assert a concrete entity:

       (: f1 (Dog dog_001) (STV 1.0 1.0))

2. Query with a variable:

       (: $prf (Dog $x) $tv)

3. Use a rule conclusion with a variable not bound by premises only with care. The system can create rule-tied existential/skolem-like terms for such unbound conclusion variables, but NL translators should avoid unbound conclusion variables unless an intentionally anonymous generated entity is desired.

### 6.3 Cardinal quantification: exactly N, at least N, more than N

There is no dedicated cardinal quantifier operator.

Represent counts using explicit facts or aggregation:

- Assert a count/cardinality fact:

      (: c1 (Cardinality (DogsIn room1) 3) (STV 1.0 1.0))

- Derive a count with `FoldAll` or `FoldAllValue`.
- Compare distribution-valued counts with `GreaterThan` / `>`.

For “more than N”, use a count distribution plus `GreaterThan`.

For “exactly N”, either assert an explicit cardinality fact or use `Compute`/aggregation patterns appropriate to the numeric representation. There is no special `Exactly` operator.

### 6.4 Vague quantifiers: most, many, few, majority

There are no built-in natural-language quantifier operators for “most”, “many”, “few”, “a majority of”, etc.

Represent them indirectly by:

- aggregating counts with `FoldAll` / `FoldAllValue`;
- computing ratios or thresholds with `Compute`;
- comparing with `GreaterThan`;
- assigning an `STV` strength/confidence to a proposition such as `(MostDogsBark group1)` if the vague quantifier is modeled as an uncertain assertion.

Example sketch for “a majority”:

    derive count of members
    derive count of members satisfying property
    compute or model ratio
    compare ratio/count distribution to threshold
    conclude (MajorityHaveProperty group property)

The exact ratio machinery must be encoded with available `Compute` and aggregation functions; there is no dedicated majority operator.

### 6.5 Negation scope

`(Not expr)` scopes only over `expr`.

Example:

    (Not (Dog $x))

It negates the TV of a proof of `(Dog $x)`. There is no separate quantifier-negation scope syntax, so NL constructions such as “not every” or “no” must be modeled explicitly using rules, classes, counts, or truth-value negation.

### 6.6 Nesting

S-expressions can be nested freely as terms, and compound connectors such as `And` can contain nested propositions. However, there is no explicit nested quantifier syntax. Scope is represented structurally by where variables occur in rule premises, conclusions, and nested terms.

## 7. Entity identity and representation

### 7.1 Identity model

The chainer has no built-in real-world entity resolution. Symbols are syntactic labels and match by exact symbolic identity.

Examples:

    fido
    alice
    paris
    paris_fr
    person_ben_001
    city_paris_fr

If two expressions use the same atom, they refer to the same entity for reasoning purposes. If they use different atoms, they are different unless you add your own equivalence/same-entity predicates and rules.

### 7.2 Avoiding name collisions

Natural-language names are often ambiguous. A translator should generate stable unique IDs rather than raw surface names when ambiguity matters.

Recommended:

    ben_person_001
    ben_person_002
    paris_fr_city
    paris_tx_city

Then optionally add naming/label facts using a user-defined predicate:

    (: n1 (Name ben_person_001 Ben) (STV 1.0 1.0))
    (: n2 (Name paris_fr_city Paris) (STV 1.0 1.0))

There is no built-in `Name` predicate; it is just a normal user predicate.

### 7.3 Classes and instances

Use unary predicates for instance-of-class:

    (: f1 (Person alice) (STV 1.0 1.0))
    (: f2 (Dog fido) (STV 1.0 1.0))
    (: f3 (City paris_fr_city) (STV 1.0 1.0))

Subclass/type rules are ordinary implications:

    (: dog_is_animal
       (Implication
          (Premises (Dog $x))
          (Conclusions (Animal $x)))
       (STV 1.0 1.0))

### 7.4 Pronouns and deictic entities

There is no built-in convention for “I”, “we”, “you”, “here”, or “now”.

If the referent is known from context, map it to a concrete entity ID:

    speaker_001
    addressee_001
    conversation_group_001

If the referent is unknown, do not invent a globally meaningful entity. Either skip the assertion/query, ask for resolution, or use an explicitly context-local placeholder such as `unknown_speaker_ctx123` only if the application can manage that identity.

### 7.5 Expressions as entities

Nested expressions can be used as terms/entities:

    (i max)
    (Pair alpha 1)
    (XY 10.0 100.0)

These are syntactic compound terms. They have no special identity semantics beyond exact structural matching unless rules give them meaning.

## 8. Practical generation guidelines

1. Always wrap assertions and queries in `(: ... ... ...)`.
2. For `add_atom()`, use a non-variable proof id and a supported TV.
3. For `query()`, use a variable proof id, usually `$prf`.
4. Use `STV` for truth; use distributions for uncertain numeric values.
5. Prefer distribution-valued arguments plus `STV` for facts about measurements:

       (: h1 (HeightDist group1 alice (ParticleFromNormal 160.0 2.0)) (STV 1.0 1.0))

6. Translate “all/every/if” into `Implication`.
7. Translate “and” in rule antecedents into multiple `Premises` or explicit `And`.
8. Translate numeric derivations with `Compute`.
9. Translate counts/aggregates with `FoldAll` or `FoldAllValue`.
10. Translate uncertain numeric comparisons with `GreaterThan` / `>`.
11. Avoid unbound variables in rule conclusions unless intentionally creating anonymous/skolem-like entities.
12. Use unique entity IDs; add user-defined name facts if human-readable labels are needed.
