
# PeTTaChainer language / API analysis

This analysis is based on the repository source, especially `pettachainer/pettachainer.py`, `pettachainer/pln_validator.py`, `pettachainer/LANGUAGE_SPEC.md`, `pettachainer/LLM_RULE_SPEC.md`, `pettachainer/metta/compile.metta`, `pettachainer/metta/tv_formulas.metta`, `pettachainer/metta/dist_formulas.metta`, `pettachainer/metta/compiled_query_runtime.metta`, and the MeTTa/Python tests.

The most important practical distinction is:

- External Python callers pass bare expressions to `PeTTaChainer.add_atom()` and `PeTTaChainer.query()`.
- They do not pass internal runtime commands such as `!(compileadd ...)` or `!(query ...)`.

---

## 1. Expression format

### Bare statement format for `add_atom(atom: str)`

Canonical external form:

`(: proof-id statement-type truth-value)`

Examples:

`(: d1 (Dog fido) (STV 1.0 1.0))`

`(: h1 (HeightDist g1 alice (PointMass 160.0)) (STV 1.0 1.0))`

`(: r1 (Implication (Premises (Dog $x)) (Conclusions (Animal $x))) (STV 1.0 1.0))`

The Python method `add_atom()` first evaluates the string with internal `!(eval ...)`, validates the evaluated result with `check_stmt()`, then wraps it internally as:

`!(compileadd <private-kb-id> <evaluated-statement>)`

External callers should not include `!(compileadd ...)`.

Validator constraints for statements:

- The evaluated expression must match `(: $prf $stmt $tv)`.
- The proof slot must not be a variable.
- The truth-value slot must not be a variable.
- The truth-value slot must match one of the supported TV/distribution forms listed below.
- A statement whose type is a variable is not useful: the compiler returns no compiled addition for variable `$Type`, so avoid `(: p $x (STV ...))`.

### Bare query format for `query(atom: str, steps=100, ...)`

Canonical external form:

`(: $proofVar type-pattern $tvVar)`

Examples:

`(: $prf (Dog fido) $tv)`

`(: $prf (Dog $x) $tv)`

`(: $prf (AvgHeightDist g1 $avgDist) $tv)`

`(: $prf (And (A) (B)) $tv)`

The Python method `query()` first evaluates the string with internal `!(eval ...)`, validates it with `check_query()`, then wraps it internally as:

`!(query steps <private-kb-id> <evaluated-query>)`

External callers should not include `!(query ...)`.

Validator constraints for queries:

- The evaluated expression must match `(: $prf $stmt $tv)`.
- The proof slot must be a variable.
- The type pattern may contain constants and/or variables.
- The TV slot is normally a variable such as `$tv`; the validator only enforces that the proof slot is variable, but downstream users should use a TV variable when retrieving truth values.

### Internal storage/runtime forms

The compiler stores/internalizes atoms with a KB/context prefix:

`(: kb proof type tv)`

It also emits internal rule clauses of the form:

`rules (premises |- conclusion)`

and CPU helper goals such as:

`(CPU function args result)`

These are implementation details. Do not use them as the external expression format for the Python API.

## 2. Built-in operators and connectors

### Statement scaffold

`(: proof-id type tv)`

Stores an asserted fact or rule with a proof identifier and a truth value.

### Rule scaffold

`Implication`, `Premises`, and `Conclusions` are the rule structure keywords:

`(Implication (Premises premise1 premise2 ...) (Conclusions conclusion1 conclusion2 ...))`

Rules are asserted by placing the `Implication` term in the type slot of a statement:

`(: ruleName (Implication (Premises ...) (Conclusions ...)) (STV s c))`

### Plain predicates

Any ordinary S-expression can be a predicate/fact type:

`(Dog fido)`

`(In room1 kid1)`

`(HeightDist g1 alice $heightDist)`

There is no schema declaration mechanism in the inspected chainer source. Predicate names, arities, and argument meanings are conventions established by the facts/rules you add.

### Compound logical connectors: `And`, `Or`, `LikelierThan`

The compiler recognizes compound source types whose head is one of:

`And`, `Or`, `LikelierThan`

Examples:

`(And (A) (B))`

`(Or (A) (B))`

`(LikelierThan (HypothesisA) (HypothesisB))`

The compiler can build adapter/projection rules for compound sources and can query compound expressions, as shown by tests querying `(And (A) (B))`.

Truth functions from `tv_formulas.metta`:

- `AndFormula`: for two STVs, strength = min strengths, confidence = min confidences.
- `OrFormula`: for two STVs, strength = min strengths, confidence = max confidences. This is not standard probabilistic union.
- `LikelierThanFormula`: compares two STVs by strength and returns the one with greater strength, with confidence = min confidences.
- `AndProjection` and `OrProjection`: pass through the STV unchanged when projecting compound children.

Multiple premises in an implication are accumulated with `AndFormula`.

### `Compute`

Premise helper:

`(Compute function (arg1 arg2 ...) -> $out)`

It compiles to a CPU call:

`(CPU function (arg1 arg2 ...) $out)`

The function is evaluated by the MeTTa runtime. Examples in tests use lambdas such as `(|-> ($acc $elem) (+ $acc $elem))` and arithmetic functions such as `+`, `*`.

### `FoldAll`

Premise helper:

`(FoldAll pattern value init fold-function -> $out)`

Semantics: aggregate over all facts matching `pattern`; extract `value` from each match; start from `init`; combine via `fold-function`; bind the final result to `$out`.

Compiler lowering:

`FoldAll` becomes an internal `FoldAllCompiled` CPU call with `unit-stv` result-TV behavior.

Typical example:

`(FoldAll (Score $name $n) $n 0 (|-> ($acc $elem) (+ $acc $elem)) -> $total)`

### `FoldAllValue`

Premise helper:

`(FoldAllValue pattern init fold-function -> $out)`

Semantics: aggregate over all matching facts, but the extracted value is the matched fact TV (`extract-tv`). This is used for distribution/counting patterns where each fact’s truth value contributes probabilistically.

Typical distribution-count example:

`(FoldAllValue (In $room $kid) (ParticleFromPairs ((0 1.0))) ParticleAddBernoulliFromSTV -> $dist)`

### `AverageDist`

Premise helper:

`(AverageDist pattern value -> $outDist)`

Semantics: match all facts satisfying `pattern`, extract distribution value `value`, sum/count them with `DistSumCountAcc`, and return the average distribution.

Example:

`(AverageDist (HeightDist $g $person $heightDist) $heightDist -> $avgDist)`

### `MapDist`

Premise helper:

`(MapDist function fact-pattern inputDist -> $outDist)`

Semantics: match `fact-pattern`, extract/bind `inputDist`, apply a unary distribution map, and bind `$outDist`.

Compiler lowering uses `DistMapFormula`.

Canonical shape:

`(MapDist f (DistFact ... $inDist) $inDist -> $outDist)`

### `Map2Dist`

Premise helper:

`(Map2Dist function fact-pattern-A distA fact-pattern-B distB -> $outDist)`

Semantics: match two distribution-valued facts, apply a binary distribution map, and bind `$outDist`.

Compiler lowering uses `DistMap2Formula`.

Canonical shape:

`(Map2Dist f (DistFactA ... $distA) $distA (DistFactB ... $distB) $distB -> $outDist)`

Example from rectangle area tests:

`(Map2Dist * (LengthDist $rect $lengthDist) $lengthDist (WidthDist $rect $widthDist) $widthDist -> $areaDist)`

### `Not`

Premise helper:

`(Not expr)`

Compiler lowering requires a match for `expr`, obtains its TV, then applies `NotFormula`.

Important pitfall: this is not negation-as-failure. `(Not expr)` does not succeed merely because `expr` is absent. It succeeds when `expr` is found and its STV can be negated.

Truth function:

`NotFormula (STV s c)` returns `(STV (- 1 s) c)`.

### `GreaterThan` and `>`

Premise helper forms:

`(GreaterThan $dist threshold)`

`(> $dist threshold)`

`(GreaterThan $distA $distB)`

`(> $distA $distB)`

Compiler behavior:

- If the second argument is syntactically a variable, it compiles as distribution-vs-distribution comparison using `DistGreaterThanDistFormula`.
- Otherwise it compiles as distribution-vs-threshold comparison using `DistGreaterThanFormula`.

Usual intended forms:

- Numeric threshold: bind a distribution first, then use `(GreaterThan $dist 1)` or `(> $dist 1)`.
- Distribution comparison: bind two distributions, then use `(GreaterThan $distA $distB)`.

### Lower-level truth/formula functions

These are defined in `tv_formulas.metta` and may appear internally or be used in MeTTa-level evaluation:

`MpFormula`

`AndFormula`

`OrFormula`

`LikelierThanFormula`

`AndProjection`

`OrProjection`

`DistGreaterThanFormula`

`DistGreaterThanDistFormula`

`NotFormula`

`InversionFormula`

`Equal`

`NotEqual`

`MpFormula` combines an implication TV and premise TV:

`MpFormula (STV abs abc) (STV as ac)` returns `(STV (* abs as) (* 0.9 (min abc ac)))`.

`InversionFormula` is used by compiler-generated inverse implications.

`Equal` returns MeTTa equality `==`; `NotEqual` returns its negation.

### Distribution helper functions

Defined mainly in `dist_formulas.metta`:

- `ParticleFromPairs`
- `PointMass`
- `ParticleFromNormal`
- `ParticlePairs`
- `ParticleMap`
- `ParticleMap2`
- `ParticleAddBernoulliFromSTV`
- `DistMapFormula`
- `DistMap2Formula`
- `DistSumCountAcc`
- `DistAverageFromSumCount`
- `ParticleStoreCount`
- `ParticleStoreClear`
- `ParticleStorePruneKB`
- `ParticleSetBudget`
- `ParticleGetBudget`

Most source-level distribution formula implementations are particle-oriented. `NatDist` and `FloatDist` are accepted/documented exact discrete TV forms, but the main helper formulas in the loaded chainer source are implemented for particle distributions.

## 3. Truth values and uncertain numeric values

### `STV`

Canonical form:

`(STV strength confidence)`

Meaning:

- `strength`: belief/probability-like mass, conventionally in `[0, 1]`.
- `confidence`: evidence/reliability, conventionally in `[0, 1]`.

`STV` is for truth uncertainty about a proposition. It is not intended to encode measurement/value uncertainty.

Examples:

`(: d1 (Dog fido) (STV 1.0 1.0))`

`(: in12 (In room1 kid2) (STV 0.5 1.0))`

### Distribution-valued uncertainty

Supported/validated distribution TV forms:

`(NatDist ((value probability) ...))`

`(FloatDist ((value probability) ...))`

`(ParticleDist ref)`

`(ParticleDist ref scale)`

`(PointMass x)`

`(ParticleFromNormal mu sigma)`

`(ParticleFromPairs ((x1 w1) (x2 w2) ...))`

The constructors in `dist_formulas.metta` produce particle-backed distributions:

- `ParticleFromPairs` stores weighted particles and returns `(ParticleDist pid 1.0)`.
- `PointMass x` is shorthand for a single weighted sample at `x`.
- `ParticleFromNormal mu sigma` uses a deterministic 9-point normal-like kernel around `mu` scaled by `sigma`.
- `ParticleDist pid scale` is an opaque reference into `&particle_store`.

Recommended modeling pattern from the LLM rule spec:

- Keep fact truth in the statement TV slot as `STV`.
- Put numeric distributions as ordinary predicate arguments.

Good examples:

`(: h1 (HeightDist g1 alice (PointMass 160.0)) (STV 1.0 1.0))`

`(: h2 (HeightDist g1 bob (ParticleFromNormal 170.0 2.0)) (STV 1.0 1.0))`

The validator also accepts distribution forms in the TV slot, e.g. `(: s2 (HeightDist g1 alice) (PointMass 170.0))`, but the documented modeling advice is to separate truth uncertainty (`STV`) from value uncertainty (distribution term arguments).

### Particle confidence semantics

For particle threshold/comparison formulas:

- Normalize particle weights.
- Effective sample size: `N_eff = 1 / sum(w_i^2)`.
- Confidence: `N_eff / (N_eff + 20)`.
- For distribution-vs-distribution comparisons, confidence is the minimum of the two particle confidences.

`ParticleAddBernoulliFromSTV` uses `tv-probability`, which for an STV is `clamp01(strength * confidence)`; non-STV inputs default to probability `1.0`.

## 4. Rule templates and logical relations

### Standard if-then rule

Bare statement form:

`(: ruleName (Implication (Premises premise1 premise2 ...) (Conclusions conclusion1 conclusion2 ...)) (STV s c))`

Example:

`(: dogAnimalRule (Implication (Premises (Dog $x)) (Conclusions (Animal $x))) (STV 1.0 1.0))`

Variables in rules use MeTTa variable syntax: `$x`, `$room`, `$dist`, etc.

### Multiple premises

Multiple premises are conjoined through the compiler using `AndFormula`.

Example:

`(: r (Implication (Premises (A $x) (B $x)) (Conclusions (C $x))) (STV 1.0 1.0))`

### Multiple conclusions

The compiler converts conclusion lists into a sequence expression via `seq2expr`; multiple conclusions are effectively represented as an `And` expression.

Example shape:

`(Conclusions (C1 $x) (C2 $x))`

### Derived distribution rules

Average height example:

`(: avgHeightDistRule (Implication (Premises (Group $g) (AverageDist (HeightDist $g $person $heightDist) $heightDist -> $avgDist)) (Conclusions (AvgHeightDist $g $avgDist))) (STV 1.0 1.0))`

Rectangle area example:

`(: areaDistRule (Implication (Premises (Rectangle $rect) (Map2Dist * (LengthDist $rect $lengthDist) $lengthDist (WidthDist $rect $widthDist) $widthDist -> $areaDist)) (Conclusions (AreaDist $rect $areaDist))) (STV 1.0 1.0))`

Probabilistic count example:

`(: cntKidInParticleRule (Implication (Premises (Room $room) (FoldAllValue (In $room $kid) (ParticleFromPairs ((0 1.0))) ParticleAddBernoulliFromSTV -> $dist)) (Conclusions (CntKidInParticle $room $dist))) (STV 1.0 0.8))`

### Inverse implications

The compiler can generate inverse implication support internally, except when:

- The proof id matches `(mined_implication ... ...)`.
- The proof id matches `(no_inverse ...)`.
- The compiled premise side contains a CPU helper.

This is an internal reasoning optimization/feature, not a separate external rule syntax downstream users normally need.

### Skolemization of conclusion-only variables

If a conclusion contains variables not present in the premise side, `compile.metta` skolemizes them internally as terms of shape:

`(exists rule idx premise-vars)`

There is no user-facing existential quantifier syntax; this is an internal generated witness term.

## 5. Query patterns

The external Python query API expects the bare form:

`(: $proofVar typePattern $tvVar)`

The proof variable is mandatory for validation.

Common patterns:

- Ask whether a ground fact is known/derivable:

  `(: $prf (Dog fido) $tv)`

- Retrieve bindings:

  `(: $prf (Dog $x) $tv)`

- Retrieve a derived distribution:

  `(: $prf (AvgHeightDist g1 $avgDist) $tv)`

- Query a compound expression:

  `(: $prf (And (A) (B)) $tv)`

- Broad query over any type is theoretically handled by `compileQuery` when the type slot is variable, e.g. `(: $prf $type $tv)`, but downstream translators should prefer specific type patterns.

What must be variable vs constant:

- Proof slot: must be a variable, e.g. `$prf`.
- Type pattern: may be ground or may contain variables.
- TV slot: normally should be a variable, e.g. `$tv`, to retrieve truth values.
- Constants are bare symbols/numbers such as `fido`, `g1`, `countryA`, `170.0`.
- Variables begin with `$`.

Invalid for Python `query()`:

`(: proof1 (Dog fido) $tv)` because proof is not variable.

`!(query 10 kb (: $prf (Dog fido) $tv))` because external callers must not include the internal runtime wrapper.

## 7. Constraints and pitfalls

### Do not pass internal wrappers to the Python API

Use:

`handler.add_atom("(: d1 (Dog fido) (STV 1.0 1.0))")`

not:

`handler.add_atom("!(compileadd kb (: d1 (Dog fido) (STV 1.0 1.0)))")`

Use:

`handler.query("(: $prf (Dog fido) $tv)")`

not:

`handler.query("!(query 10 kb (: $prf (Dog fido) $tv))")`

The Python wrapper itself adds `!(compileadd ...)` and `!(query ...)`.

### Statement proof IDs cannot be variables

Invalid statement:

`(: $prf (Dog fido) (STV 1.0 1.0))`

### Statement TV cannot be a variable

Invalid statement:

`(: d1 (Dog fido) $tv)`

### Query proof must be a variable

Invalid query:

`(: proof1 (Dog fido) $tv)`

### TV forms are restricted

Invalid statement TV:

`(CustomTV 0.9)`

The validator only accepts the supported TV/distribution forms listed above.

### `STV` is not value uncertainty

Do not encode “height is around 170” as `(STV 0.7 0.9)`. Use a distribution term such as `(ParticleFromNormal 170.0 2.0)` as an argument to a measurement predicate, with a separate `STV` for truth of the measurement fact.

### `Not` is not absence-based negation

`(Not expr)` requires `expr` to match and then negates the matched TV. It does not mean “there is no proof of expr.”

### `GreaterThan` dispatch depends on syntactic variable status of the second argument

The compiler chooses distribution-vs-distribution comparison if the second argument is a variable. Use a numeric literal/constant threshold for threshold comparisons.

Good:

`(GreaterThan $cnt 1)`

Good after both distributions are bound:

`(GreaterThan $distA $distB)`

### Use constructors instead of hand-written `ParticleDist` IDs

`ParticleDist` is an opaque reference into the particle store. Prefer:

`(PointMass 160.0)`

`(ParticleFromNormal 170.0 2.0)`

`(ParticleFromPairs ((170 0.5) (180 0.5)))`

rather than manually inventing `(ParticleDist pid scale)`.

### No infix logical syntax

Use prefix S-expressions only. There is no supported syntax like `A -> B`, `A and B`, or `forall x`.

### Exact `Implication` structure matters

Use exactly:

`(Implication (Premises ...) (Conclusions ...))`

Do not omit `Premises` or `Conclusions`.

### Case matters

The current chainer uses `STV`, not lowercase `stv`, in valid API statements. An old/demo `tuffy.metta` file uses different forms such as `stv` and `Inheritance`, but that is not the current PeTTaChainer API pattern.

### No schema/type enforcement

The chainer does not enforce predicate arity or argument types. `(Dog fido)`, `(Dog fido spot)`, and `(dog fido)` are different syntactic terms.

## 8. Quantification and scope

There are no dedicated user-facing quantifier operators in the chainer source:

- No `ForAll`
- No `Exists`
- No `forall`
- No cardinal quantifier syntax such as `Exactly`, `AtLeast`, or `AtMost`

### Universal quantification

Rule variables are implicitly universally scoped over the implication rule. For example:

`(: r (Implication (Premises (Dog $x)) (Conclusions (Animal $x))) (STV 1.0 1.0))`

means, operationally, for any binding of `$x` satisfying `(Dog $x)`, derive `(Animal $x)`.

Scope is the whole rule expression. There is no nested quantifier syntax and no explicit quantifier precedence.

### Existential meaning

Existential claims are represented indirectly:

1. By explicit witness constants, e.g. assert `(Owns alice dog1)` using a concrete symbol `dog1`.
2. Internally, if a rule conclusion contains variables not appearing in the premise side, the compiler skolemizes them into generated terms of shape `(exists rule idx premise-vars)`.

The internal `exists` term is not a general user-facing quantifier operator.

### Cardinality / counting

Cardinality-like reasoning is expressed through aggregation, not through quantifier syntax.

Examples:

- Use `FoldAll` to count/sum exact matches.
- Use `FoldAllValue` with `ParticleAddBernoulliFromSTV` to build a distribution over counts.
- Use `GreaterThan` / `DistGreaterThanFormula` to ask threshold questions about count distributions.

### Negation and quantifier interaction

There is no formal nested quantifier/negation scope system. `(Not expr)` simply matches `expr`, reads its TV, and applies `NotFormula`.

### Truth values and quantification

Quantified formulas do not carry special quantifier TVs because there are no quantifier formulas. Rule statements carry an ordinary TV in their statement TV slot, and premise/conclusion truth propagation is handled by the formula functions such as `AndFormula` and `MpFormula`.

## 9. Entity identity and representation

The chainer has no built-in real-world entity identity system. Symbols are syntactic labels. Two occurrences of the same atom name match; different atom names do not match unless connected by rules you write.

Examples:

- `alice` is the same symbol wherever `alice` appears.
- `Alice`, `alice`, and `alice_1` are distinct symbols.
- `Paris` as a person and `Paris` as a city would be conflated if represented by the same symbol.

Recommended practice for named entities:

- Use stable unique identifiers as constants, e.g. `person_ben_001`, `city_paris_fr`, `city_paris_tx`.
- If surface names matter, add your own naming facts, e.g. `(Name person_ben_001 "Ben")`, but note that `Name` is not a built-in semantic primitive in the chainer; it is just another predicate if you choose to use it.
- Represent class membership with ordinary predicates, e.g. `(Person person_ben_001)`, `(City city_paris_fr)`, `(Dog fido)`. There is no special built-in `Instance` or `Member` operator in the current chainer API.
- An old `tuffy.metta` file contains `Inheritance` examples, but these use a different/demo syntax and should not be treated as the PeTTaChainer API convention.

Pronouns:

- There is no built-in convention for `I`, `we`, or `you`.
- If the referent is known, resolve the pronoun to a unique entity constant before adding facts.
- If the referent is unknown, skip the pronoun-dependent assertion or represent uncertainty outside the chainer; do not assert facts about a literal symbol like `you` unless that is deliberately your entity ID.

# Primitives cheat sheet

This section is the consolidated quick reference for downstream translators. It lists the primitives documented above and only those primitives.

## Expression scaffolding

`(: proof-id type tv)` — Bare statement form for `add_atom`; asserts a fact or rule.

`(: $prf typePattern $tv)` — Bare query form for `query`; proof slot must be a variable.

`proof-id` — Non-variable symbol identifying an assertion/rule proof.

`$var` — MeTTa variable syntax used in rules and queries.

## Internal wrappers to avoid in Python API

`!(compileadd kb stmt)` — Internal MeTTa command used by the wrapper; do not pass to `add_atom()`.

`!(query steps kb queryPattern)` — Internal MeTTa command used by the wrapper; do not pass to `query()`.

`(: kb proof type tv)` — Internal compiled/storage atom shape with KB context.

`(CPU function args result)` — Internal compiled computation goal.

`rules (premises |- conclusion)` — Internal compiled rule clause.

## Rule structure

`(Implication (Premises premise1 premise2 ...) (Conclusions conclusion1 conclusion2 ...))` — If all premises hold, derive the conclusions.

`(Premises premise1 premise2 ...)` — Premise list inside an implication.

`(Conclusions conclusion1 conclusion2 ...)` — Conclusion list inside an implication.

## Predicate/fact forms

`(Predicate arg1 arg2 ...)` — Plain user-defined predicate; predicate names and arities are conventional.

`(Class entity)` — Common idiom for class membership, e.g. `(Dog fido)` or `(Person alice)`; not a special primitive.

## Logical/connective forms

`(And expr1 expr2 ...)` — Compound conjunction recognized by the compiler; combines TVs via `AndFormula`.

`(Or expr1 expr2 ...)` — Compound disjunction-like connector recognized by the compiler; combines TVs via `OrFormula`.

`(LikelierThan expr1 expr2)` — Compound comparison connector; returns the likelier STV by strength.

`(Not expr)` — Premise helper that matches `expr` and negates its TV; not negation-as-failure.

## Computation and aggregation premise helpers

`(Compute function (arg1 arg2 ...) -> $out)` — Run a MeTTa function and bind its result.

`(FoldAll pattern value init fold-function -> $out)` — Aggregate extracted values over all matching facts.

`(FoldAllValue pattern init fold-function -> $out)` — Aggregate matched fact TVs over all matching facts.

`(AverageDist pattern value -> $outDist)` — Average distribution-valued matches.

`(MapDist function factPattern inputDist -> $outDist)` — Apply unary distribution map to one matched distribution.

`(Map2Dist function factPatternA distA factPatternB distB -> $outDist)` — Apply binary distribution map to two matched distributions.

## Comparison premise helpers

`(GreaterThan $dist threshold)` — Distribution-vs-numeric-threshold premise; compiles to `DistGreaterThanFormula`.

`(> $dist threshold)` — Alias form for threshold comparison.

`(GreaterThan $distA $distB)` — Distribution-vs-distribution premise when second argument is a variable; compiles to `DistGreaterThanDistFormula`.

`(> $distA $distB)` — Alias form for distribution comparison.

## Truth-value forms

`(STV strength confidence)` — Simple truth value for proposition truth.

`(NatDist ((value probability) ...))` — Exact discrete natural/integer-valued distribution TV form, documented/validated.

`(FloatDist ((value probability) ...))` — Exact discrete float-valued distribution TV form, documented/validated.

`(ParticleDist ref)` — Accepted particle distribution reference form; prefer constructors.

`(ParticleDist ref scale)` — Particle distribution reference with scale; constructors produce this shape.

## Distribution constructors and value forms

`(ParticleFromPairs ((x1 w1) (x2 w2) ...))` — Build a particle distribution from weighted samples.

`(PointMass x)` — Build a degenerate particle distribution concentrated at `x`.

`(ParticleFromNormal mu sigma)` — Build a deterministic 9-point normal-like particle approximation.

`(ParticlePairs particleDist)` — Return weighted particle pairs for a particle distribution.

## Distribution formula/helper functions

`(DistGreaterThanFormula dist threshold)` — Return `STV(P(dist > threshold), confidence)`.

`(DistGreaterThanDistFormula distA distB)` — Return `STV(P(distA > distB), confidence)`.

`(ParticleAddBernoulliFromSTV particleDist stv)` — Update a count distribution by adding a Bernoulli trial whose probability is derived from an STV.

`(ParticleMap function particleDist)` — Apply unary function to particle values.

`(ParticleMap2 function particleDistA particleDistB)` — Apply binary function to pairs of particle values.

`(DistMapFormula function dist)` — Distribution-map formula; implemented via `ParticleMap`.

`(DistMap2Formula function distA distB)` — Binary distribution-map formula; implemented via `ParticleMap2`.

`(DistSumCountAcc (SumCount sumDist count) hdist)` — Accumulator helper for distribution averaging.

`(DistAverageFromSumCount (SumCount sumDist count))` — Convert sum/count accumulator into an average distribution.
